### 1. Synthetic Dataset Scope vs. Real-World Generalization
* **Measured State**: All performance metrics are evaluated strictly on synthetic datasets generated by `data/generator.py` (**80 technical institutions**, **164 FDR instruments**, **328+ rendered PDF/scanned documents** across 5 fictional bank layouts: Bharat National Bank, Apex Commercial Bank, Gramin Vikas Bank, Hindustan Mercantile Bank, Pragati Cooperative Bank).
* **Limitation**: While scan noise simulation (OpenCV affine rotation $\pm 1.5^\circ$, Gaussian blur, Poisson noise, paper contrast) was injected, real-world bank deposit receipts exhibit vast diversity (dot-matrix printing, carbon copies, regional language rubber stamps, handwritten counter-signatures, physical tears, and skewed mobile camera photos). Real-world field extraction accuracy is expected to be lower than synthetic benchmarks until trained on historical AICTE physical archives.
* **Mitigation / Roadmap**: DepoSafe's **4-Source Dual-Truth Ledger** (`SUBMITTED`, `AI_EXTRACTED`, `BANK_CONFIRMED`, `OFFICER_VERIFIED`) ensures no AI extraction is ever authoritative on its own. Low confidence extractions ($< 0.70$) automatically flag `"needs human confirmation"`, and officers retain final authority with mandatory recorded justifications.

### 2. Bank Verification Adapter vs. Live Core Banking (CBS / SFMS)
* **Measured State**: Bank verifications operate through `BankVerificationAdapter` and `SimulatedBankService`. All automated responses carry the statutory watermark notice: `SIMULATED, not a real bank verification`.
* **Limitation**: Due to regulatory and privacy restrictions during hackathon development, the system is not connected to live Reserve Bank of India (RBI) SFMS gateways, NeSL e-BG (electronic Bank Guarantee) networks, or commercial bank Core Banking APIs.
* **Mitigation / Roadmap**: The adapter architecture strictly implements the industry-standard SFMS (`IFN 760` Structured Financial Messaging System) message structures and ISO 20022 Open Banking payloads (detailed in `docs/BANK_INTEGRATION_SPEC.md`). Transitioning to production requires signing bilateral API MOUs with participating Scheduled Commercial Banks or routing through NeSL / NPCI.

### 3. Empirical Discrepancies in Anomaly & Forensics Detection (Resolved in Phase 11b & 11c)
* **Measured State (Single Benchmark Run: Commit `5fa2edd`)**:
  * In `scripts/benchmark_anomaly.py`, running on the full synthetic corpus of 164 instruments:
    * Duplicate Detection: **F1 100.00%** (Precision: **100.0%**, Recall: **100.0%**) (up from 53.85% baseline)
    * Forensic Tamper Detection: **F1 82.05%** (Precision: **94.1%**, Recall: **72.7%**)
    * Cross-Document Maturity Mismatch Detection: Precision: **76.5%**, Recall: **54.2%**, **F1: 63.41%** (up from 36.9% precision baseline)
    * Mean Review Priority Score on Clean Documents: **6.6 / 100** (Dev Set) and **7.5 / 100** (Held-Out Set)
    * Hero Case (`BNB-DEL-HERO-1000`) Review Priority Score: **80.0 / 100** (Target: 60.0&ndash;80.0, **Verified: True**)
* **Root Cause Diagnostics, Generator Fixes & Defensible Boundaries**:
  1. *Duplicate Collision Resolution & Label Mismatch (Phase 11c Audit)*:
     * *Root Cause Diagnosed*: The synthetic generator (`data/generator.py`) previously omitted the assignment logic for the `same_bank_and_number_different_file` category, generating unique FDR numbers while labelling them as duplicates.
     * *Generator Resolution*: Fixed `data/generator.py` to correctly assign collision pool identifiers `(bank_name, fdr_number)` to newly rendered distinct PDF files.
     * *Empirical Outcome*: Duplicate detection achieved **100.0% Precision and 100.0% Recall (F1 100.00%)** across both the dev set and held-out dataset.
     * *pHash Policy*: Perceptual hash (pHash) Hamming distance $\le 2$ matches uniform ReportLab template borders across banks, causing 119 false collisions if used as an automated binary trigger. Therefore, **pHash does NOT feed `has_collision`**. It serves strictly as an advisory visual similarity metric for human review.
  2. *Forensics Circularity Audit & Generator-Aligned Detectors*:
     * *Generator-Aligned Signals*: The detector rules checking for hex color `#B81C1C` and the string `[MODIFIED]` are explicitly **generator-aligned**. In the real world, fraudulent actors do not flag altered values in red text or label their alterations `[MODIFIED]`.
     * *Unmodified-Marker Empirical Test (`backend/tests/test_unmodified_marker.py`)*:
       - **Test A (Mismatched font family, black ink `#000000`, no markers)**: Single-doc font scanner successfully flags `FONT_FAMILY_DISCONTINUITY` (`Courier` spliced amidst `Helvetica`).
       - **Test B (Same font family `Helvetica`, black ink `#000000`, no markers, stripped metadata)**: Single-document heuristic scanners **FAIL** (cannot distinguish between black Helvetica spans).
       - **Real-World Defense**: Test B is **100% CAUGHT by the 4-Source Dual-Truth Ledger** (`CrossDocumentReconciler` and `BankVerificationAdapter`), because the forged certificate amount contradicts the bank confirmation letter and CBS record. This proves why single-document AI heuristics are insufficient alone and validates the dual-truth architecture.
  3. *Maturity Mismatch Precision Resolution (36.9% &rarr; 76.5%)*:
     * *Root Cause Diagnosed*: In the generator, when constructing renewal chains, setting expired dates, and copying shared file bytes, `mat_d` was updated on the certificate but `bank_letter_mat` was left as an un-updated random date. The generator was physically writing mismatched dates on disk while labelling the cases as clean.
     * *Generator Resolution*: Reconciled date generation sequencing so that `bank_letter_mat` matches `mat_d` unless `maturity_mismatch_with_bank_letter` is intentionally injected.
     * *Empirical Outcome*: Mismatch precision rose from **36.9% to 76.5%** on the 164-document corpus.
  4. *PDF Metadata Scanner Strings & macOS Quartz Caveat*:
     * *Triggering Software Signatures*: Scans `Producer`, `Creator`, and `Author` against: `photoshop`, `canva`, `gimp`, `sejda`, `pdfescape`, `ilovepdf`, `smallpdf`, `foxit phantompdf`, `inkscape`, `coreldraw`, `illustrator`, `acrobat distiller`, `nitro pro`, and `wondershare`, plus chronological inversion (`creationDate != modDate`).
     * *Quartz Caveat*: macOS native PDF generation and Preview.app routinely write `Quartz PDFContext` into the Producer field. Legitimate scans produced on Apple workstations or scanner drivers would be falsely flagged if `Quartz` were blacklisted. Conversely, omitting Quartz means macOS-based manipulation must be caught by font analysis, ELA, or dual-truth cross-reconciliation.

### 4. Per-Bank Extraction Schema Calibration (Pragati Cooperative Bank & 6 Layout Schemas)
* **Measured State (Post-Calibration)**:
  * In `scripts/benchmark_extraction.py`, `PRAGATI_COOPERATIVE_BANK` layout identification accuracy rose from **0.0% to 96.0%** (24/25), with the sole unclassified document being an intentionally injected non-FDR utility bill correctly routed to `UNKNOWN_LAYOUT`.
  * Overall document extraction across all banks reached **94.81% Macro F1** (Precision: **93.19%**, Recall: **97.87%**).
  * Document classification accuracy reached **95.73%** (157/164).
* **Architecture Clarification**: The platform defines **6 layout template schemas** in `config/doc_schemas/` (5 bank-specific schemas: Bharat National Bank, Apex Commercial Bank, Gramin Vikas Bank, Hindustan Mercantile Bank, Pragati Cooperative Bank + 1 generic fallback schema `generic_fdr.yaml`).
* **Root Cause Analysis & Fix**:
  * In `config/doc_schemas/pragati_cooperative_bank.yaml`, the bank name was normalized to `"Pragati Urban Cooperative Bank"`, aliases (`PUCB`, `PRAGATI URBAN COOPERATIVE BANK`) were added, header keyword `"MEMBER FIXED DEPOSIT ACKNOWLEDGEMENT"` was included, and field regexes for `fdr_number` and `amount` were aligned with the generator template.
  * When `wrong_bank_name` is injected, the institution submits an unapproved non-scheduled cooperative bank instrument. The Document AI pipeline extracts the text faithfully, allowing the deterministic compliance engine to enforce `APH-NON-SCHEDULED-BANK-RESTRICTION`.

### 5. Meaning of "100% Rule Execution Adherence"
* **Clarification**: Documentation refers to "100% rule execution adherence" (previously termed "100% compliance accuracy"). This refers strictly to the **deterministic mathematical execution** of the rule engine (`backend/app/rules/compliance_engine.py` evaluating `config/rules/aph_2024_27_v1.yaml`).
* **Reality**: It verifies that the Python logic evaluating threshold amounts, lock-in duration, and whitelisted banks executes against the rules we wrote with zero probabilistic drift or LLM hallucination. It does NOT claim real-world legal correctness, which requires statutory gazette notification and AICTE Council interpretation. In the synthetic dataset, 94 instruments (57.3%) passed baseline rules and 70 (42.7%) failed with transparent statutory deficits.

### 6. Playwright Test Suite Runtime Requirements
* **Measured State**: `backend/tests/test_phase10_playwright_e2e.py` contains 3 end-to-end browser automation tests.
* **Limitation**: Running `pytest backend/tests/` without optional browser drivers installed errors during test collection (`ModuleNotFoundError: No module named 'playwright'`).
* **Mitigation**: Base unit and integration tests (57 tests) execute cleanly with `pytest backend/tests/ --ignore=backend/tests/test_phase10_playwright_e2e.py`. Playwright is documented as an optional browser-testing dependency requiring `pip install playwright && playwright install chromium`.

### 7. SQLite Concurrency vs. PostgreSQL 16 Production
* **Measured State**: Zero-daemon local execution uses SQLite (`deposafe.db`) with `check_same_thread: False`.
* **Limitation**: SQLite uses database-level locking for write operations. Concurrent API calls during heavy automated load testing can trigger `sqlite3.OperationalError: database is locked`.
* **Mitigation**: Production deployments run PostgreSQL 16 via `docker-compose.yml`, featuring row-level locking, MVCC, and connection pooling via SQLAlchemy 2.0.

---

### 8. Celery Beat vs. Local API-Driven Scheduling
* **Measured State**: The Maturity Radar service evaluates notification ladders (`T-90, T-60, T-30, T-15, T-7, T-0, Overdue`).
* **Limitation**: In local lightweight mode (`make run-backend`), Celery worker and Redis are disabled to allow execution on developer laptops without daemons. Background escalation sweeps are triggered synchronously via API (`POST /api/v1/lifecycle/radar/scan`) or during Demo Clock advancement.
* **Mitigation**: Docker Compose (`make up`) starts the full distributed architecture with Redis broker, Celery worker, and Celery beat scheduler for automated hourly sweeps.
